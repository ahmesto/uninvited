Linux, nftablesrefreshes itself

Set it up once:

sudo nft add table inet uninvited
sudo nft add set inet uninvited bad '{ type ipv4_addr; }'
sudo nft add chain inet uninvited input '{ type filter hook input priority -10; policy accept; }'
sudo nft add rule inet uninvited input ip saddr @bad drop

Then this script keeps the set current. Save it as /usr/local/bin/uninvited-update.sh:

#!/bin/sh
set -e
LIST=$(curl -fsS https://{{site}}/feed/tag-persistent-7d.txt \
  | grep -E '^[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+$' | paste -sd, -)
[ -n "$LIST" ] || exit 1
nft flush set inet uninvited bad
nft add element inet uninvited bad "{ $LIST }"

Run it every 30 minutes from /etc/cron.d/uninvited:

*/30 * * * * root /bin/sh /usr/local/bin/uninvited-update.sh

The download and address extraction were run against the live feed. The nftables commands are standard syntax, so try them on a test machine first. The lists currently hold IPv4 only.

A polling script that behavespython 3, no packages

It keeps a local copy and downloads again only when the list changed, using the ETag. Lists rebuild every five minutes, so there is no point asking more often.

#!/usr/bin/env python3
import os, sys, urllib.request, urllib.error

URL = "https://{{site}}/feed/tag-persistent-7d.txt"
OUT = "/var/tmp/uninvited-persistent.txt"
TAG = OUT + ".etag"

req = urllib.request.Request(URL, headers={"User-Agent": "uninvited-poll/1.0"})
if os.path.exists(TAG) and os.path.exists(OUT):
    req.add_header("If-None-Match", open(TAG).read().strip())
try:
    with urllib.request.urlopen(req, timeout=30) as r:
        body = r.read().decode()
        open(OUT, "w").write(body)
        open(TAG, "w").write(r.headers.get("ETag", ""))
        print("updated:", sum(1 for l in body.splitlines() if l and not l.startswith("#")), "addresses")
except urllib.error.HTTPError as e:
    if e.code == 304:
        print("unchanged")
    else:
        sys.exit("error: HTTP %d" % e.code)

Run twice, it printed "updated: 256 addresses" and then "unchanged".

Keep a copy in sync from the changespython 3, no packages

Instead of downloading the whole list each time, ask what was added and removed since you last looked. The first run takes a full copy and notes the time. Every run after that applies only the changes. If your copy is ever older than the two weeks of history kept here, the answer says "reset": true and the script starts over with a full copy, so it never ends up with a partial list.

#!/usr/bin/env python3
# Keep a local copy of one {{brand}} list current by asking only what changed.
import json
import os
import urllib.parse
import urllib.request

BASE = "https://{{site}}/feed"
LIST = "tag-persistent-7d"
STATE = f"/var/tmp/uninvited-{LIST}.json"


def get(path):
    req = urllib.request.Request(BASE + path, headers={"User-Agent": "uninvited-sync/1.0"})
    with urllib.request.urlopen(req, timeout=30) as r:
        return r.read().decode()


def full_copy():
    since = json.loads(get("/status.json"))["generated"]   # note the time first
    lines = get(f"/{LIST}.txt").splitlines()
    return {"since": since, "ips": sorted(x for x in lines if x and x[0] != "#")}


state = None
if os.path.exists(STATE):
    with open(STATE) as f:
        state = json.load(f)
if state:
    d = json.loads(get(f"/changes/{LIST}?since={urllib.parse.quote(state['since'])}"))
    if d["reset"]:
        state = None                      # our copy is too old, start again
    else:
        ips = (set(state["ips"]) | {a["ip"] for a in d["added"]}) - set(d["removed"])
        state = {"since": d["as_of"], "ips": sorted(ips)}
        print(f"changed: {len(d['added'])} added, {len(d['removed'])} removed, {len(ips)} addresses now")
if state is None:
    state = full_copy()
    print(f"full copy: {len(state['ips'])} addresses")
with open(STATE, "w") as f:
    json.dump(state, f)

Run it every five minutes or so, since the lists rebuild on that schedule. I ran it against a copy of this service through a first copy, a run with no changes, a host added, a host removed and a copy that was too old, and the local list matched the published one each time. Change LIST to follow any other list. Changes that happened in the same rebuild as your first copy can show up twice, which is harmless: adding an address you already have, or removing one you do not, changes nothing.

About {{brand}}
How it is built The feed rules

I put a box on the internet with the doors open on purpose. Nine services are listening. All of them are fake. Everything on the dashboard showed up uninvited.

Who runs it

I designed it and I run it. The decisions that matter are mine: the isolated VLAN, what the decoys will and will not do, the rule that a port scan never counts as an attack, and the focus on industrial protocols. Everything here is checked against live traffic.

Path in

The decoys

  • SSH runs a real key exchange through paramiko, so passwords and public key fingerprints land intact. Auth always returns AUTH_FAILED and channel requests are refused. No shell, no SFTP, no forwarding.
  • Telnet strips IAC negotiation before parsing, otherwise option bytes end up inside the username.
  • HTTP matches every request against a signature table. Dotenv exposure, Log4Shell, PHPUnit eval-stdin, Spring Actuator, IoT router RCE, and MCP endpoint discovery, which showed up for the first time this month.
  • RDP pulls the mstshash cookie from the X.224 connection request, which usually carries the username for free.
  • SIP resolves the dialed country code on INVITE, so toll fraud is obvious. Someone billing calls through a PBX I do not have.
  • SMB reports the dialect, separating EternalBlue-era scanners from anything modern.
  • Modbus is the language industrial controllers speak. The decoy is a made-up controller that answers reads, tells scanners its invented make and model, and accepts a write only for the length of one connection, then forgets it. It records whether a client looked or tried to change something, because those are different visitors.
  • Siemens S7 is how engineering software talks to a Siemens controller. The decoy completes the handshake, reports a made-up CPU and serial number when asked, answers reads with zeros, and accepts writes, stops and program transfers without doing anything. It records which of those a client tried, because stopping a controller is a different act from looking at one.
  • EtherNet/IP is the protocol Allen-Bradley and many other controllers speak. The decoy answers the identity request every scanner starts with, then reads and writes against a pretend controller, and records which. It never answers over UDP, so it cannot be used to bounce traffic at someone else.
  • DNP3 runs power and water utilities. The decoy answers the link-layer questions and acknowledges requests, and records whether a client read, wrote or tried to operate or restart the device. It is newer and less proven than the others.
  • IP camera pretends to be a network camera, on its web port and its video port. Every login fails and the passwords tried are recorded. A known camera exploit gets the answer a vulnerable camera would give, so the next step, usually a download command, is captured. Nothing is ever run.
  • Router pretends to be a home router, on its admin page and its remote-management port. Default passwords are recorded and refused. Router exploits get the answer a vulnerable router would give, and the command that follows is captured. Nothing is run.
  • AI tool server answers like a Model Context Protocol server and a model API. It lists a few tools and refuses every call, and it records what a client asks for and what it tries to make the tools or the model do.

Why those decoys

The industrial decoys are here because controllers for power, water and factories sit on the internet far more often than they should, and the traffic that looks for them is rarely published. Reading a controller and stopping one are different acts, so the decoys record which was tried, and a write or a stop command is what puts an address on the "worth a look" list.

The camera decoy exists because cameras are the easiest foothold a botnet gets: default passwords and old firmware, in very large numbers. The exploit requests it receives carry the download addresses that fill the malware URL list.

The router decoy is the same bet for home and small-office routers, which botnets recruit through the admin page and through the remote-management port some providers leave open.

The AI tool server is the newest. Tool servers and model APIs are being put on the internet quickly, and this decoy shows who is already looking for them and what they ask the tools to do. Nothing it is asked to do is done.

Nothing sent here runs

  • Every read is size-capped, every connection has a hard timeout, and a global semaphore caps concurrency.
  • Attacker input never reaches a shell, an interpreter, a file path or a SQL string. Every query is parameterised and every output escaped.
  • The unit runs with an empty CapabilityBoundingSet, ProtectSystem=strict, NoNewPrivileges, a syscall filter, and one writable directory.

Containment

The VM sits alone on its own VLAN. A gateway ACL denies that VLAN to every other network, and a second denies it the firewall's management interfaces. It resolves DNS externally, so nothing points inward.

Worth knowing if you run Omada: same-VLAN traffic is switched locally and never reaches the gateway, so no gateway ACL can stop a lateral move between two hosts sharing a segment. That is why this box got a VLAN to itself rather than joining the existing DMZ.

Reading it

  • Scanners are not attackers. Shodan, Censys, BinaryEdge and about twenty others are identified by reverse DNS rather than CIDR lists, because census8.shodan.io outlives whatever address it runs on. They are counted separately so the attack number means something.
  • Hosts cluster by behaviour, not by network. Shared credentials are the edge, union-find does the grouping. Twelve addresses replaying one list are one actor with one tool.
  • Passwords get identified. xc3511 is XiongMai camera firmware. vizxv is a Dahua DVR. ubnt is Ubiquiti out of the box. High-entropy passwords are not guesses at all, they are breach dumps being replayed.

The point

Every address that attacks this box is exported at /feed/attackers-24h.txt as plain text, one per line, with 7 day and 30 day versions beside it. Research scanners get their own list, so they never land in a blocklist. A firewall pulls it on a timer and denies it at the perimeter. The dashboard is the demo. The feed is the product.

Passwords are exported too, at /api/wordlist, ranked by frequency. Passwords only, no usernames attached and no addresses, because a frequency list is useful to other people and a pairing that resolves an account to its password is a different thing entirely.

How an address earns a place on the feed, how it is scored, and how often that turns out to be right.

What gets on the feed

An address is listed when it attacked, not when it looked. It has to be a real TCP session, because a UDP source can be forged and I will not put a victim on a block list. It has to guess a login, send an exploit or ask for a relay, at least three times. Research scanners and Tor exits get their own lists. A scanner's name only counts if it resolves back to its address, and a scanner that tries a password is an attacker.

How long it stays

An attacker leaves every list 3 days after its last attack if it is on a consumer line, 7 if it is a server, and half as long again with a score of 60 or more. expires says when. Each list is ordered by score, halved for every three quiet days, so the most active hosts come first.

The score

Zero to a hundred, the same in every file. Four signals, in one short file of tables and arithmetic you can read and argue with.

Volume10 to 40 points at 3, 10, 50 and 200 attack events in 30 days
Breadth10 for two protocols, 20 for three or more
Persistence5, 10 or 20 points for 1, 3 or 7 days or more on record
Exploit20 points for at least one named exploit attempt

Tags

Every attacker carries plain tags for what it did, like ssh-bruteforce and rdp-scan, and the main ones have their own list. Behavior maps to MITRE ATT&CK down to the sub-technique, and a CVE only appears when a request matches exactly one vulnerability. Fixed rules decide all of it, no model.

Malware URLs

When a botnet exploits a camera or a router, the request often carries a download command. I list that address once two different hosts deliver it, or the host that sent it is the host it points at, so one request cannot get a legitimate address blocked. I never fetch them, and a file name only hints at a family.

Who you might block

Each host is marked hosting, ISP or unknown, from its network number or name. A hosting address is usually one customer's server, so blocking it is low risk. A consumer ISP address can be shared or reassigned, so it leaves the lists sooner. It is a guess, and the files say so.

How often it is right

I measure it. The Threat Intel tab shows how many hosts listed a day and a week ago attacked this server again since. One server sees a small slice of the internet, so the number is a floor. I would rather publish a number that can go down than a promise.

Never listed

Public DNS resolvers, the big search crawlers, private and shared address space, and anything on my own exclude list never make it in, however they behave.
